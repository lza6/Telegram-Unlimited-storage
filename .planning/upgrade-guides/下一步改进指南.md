## 1. 概述与升级目标

Telegram Drive 将 Telegram 账号转化为无限云存储，当前版本 `v3.0.0-beta`。代码库成熟度较高，但存在明显技术债务和安全债务。本指南定义从 v3 → v4 的系统性升级路径。

### 升级哲学

| 原则 | 说明 |
|------|------|
| 🎯 **非重构，而是升级** | 不动现有架构骨架，在已有实现上增强 |
| 🔄 **渐进式迭代** | 按优先级分阶段执行，每个阶段可独立验证 |
| ✅ **全链路闭环** | 每个改动必须经过：测试 → 构建 → 运行验证 |
| 🧹 **清理旧产物** | 升级后清理屎山代码、旧版本残留、死代码 |
| 🧪 **100% 测试覆盖** | 新增代码必须配套真实测试套件 |

### 版本目标

```
v3.0.0-beta（当前）→ v4.0.0（目标）
├── 安全评级:  14/17 ✅ 通过 → 17/17 全部通过
├── 前端无障碍:  0% ARIA 覆盖 → 100% 关键路径覆盖
├── 移动端适配:  固定宽度 → 全响应式
├── 测试覆盖率:  Rust ~40% / 前端 ~5% → 80%+ / 60%+
├── 性能:  SQLite 串行瓶颈 → 连接池
└── Docker 镜像:  800MB → <400MB
```

## 2. HIGH 优先级 — 安全加固

### 2.1 [H-01] 遗留 SHA-256 API Key 哈希迁移

**文件**: `password_kdf.rs:36`

**问题**: `verify_api_key` 对旧密钥使用裸 SHA-256，无盐，彩虹表可破解。

**解决方案**:
1. 在验证通过后自动升级：检测到 legacy hash → Argon2id 重新哈希 → 写回 DB
2. 新注册/重置密钥全部使用 Argon2id

**验收标准**:
- [ ] 所有 API key 验证后自动升级到 Argon2id
- [ ] 无明文密钥存储在数据库或日志中
- [ ] 向后兼容：旧密钥在首次验证前仍然可用

### 2.2 [H-02] 管理员密码验证时序攻击

**文件**: `admin_routes.rs:188`

**问题**: `check_pwd_form` 在常量时间比较前对输入做 `.trim()`，泄露密码格式信息。

**解决方案**:
```
Before: constant_time_eq(pwd.trim(), config.access_pwd.trim())
After:  constant_time_eq(pwd, config.access_pwd.trim())  // 只 trim 存储侧
```

**验收标准**:
- [ ] 常量时间比较在输入变换之前执行
- [ ] 所有密码验证路径统一

### 2.3 [H-03] Content-Disposition 文件名注入

**文件**: `http_download.rs:86,132`

**问题**: 文件名直接嵌入 HTTP header，含引号/特殊字符时可注入。

**解决方案**: 对文件名中的 `"` 和 `\` 进行转义或 RFC 5987 编码。

**验收标准**:
- [ ] 含特殊字符的文件名下载后正确显示
- [ ] header 注入攻击向量消除

### 2.4 [H-04] CSP 强化

**文件**: `http_middleware.rs:82`

**问题**: CSP 允许 `'unsafe-inline'` 和 `unpkg.com`。

**解决方案**: 尽可能使用 nonce 策略，限制 unpkg.com 到必要资源。

**验收标准**:
- [ ] 管理 UI 正常工作
- [ ] Swagger UI 正常工作（需 nonce 适配）
- [ ] CSP 评分提升到 A+

## 3. MEDIUM 优先级 — 后端架构升级

### 3.1 [M-01] SQLite 连接池化

**文件**: `db.rs:31`

**问题**: `DbConnection` 使用 `Arc<std::sync::Mutex<rusqlite::Connection>>`，所有操作串行化，高并发下成为瓶颈。

**解决方案**: 引入 `deadpool-sqlite` 或 `r2d2-sqlite` 连接池：
- 配置 4-8 连接池大小
- 迁移所有查询到连接池 API
- WAL 模式已启用，并发读取性能大幅提升

**风险**: 需要修改 `db.rs` 全部 698 行中的查询方法签名。

**验收标准**:
- [ ] 并发上传/下载不再阻塞同一个连接
- [ ] 连接池自动回收泄漏的连接
- [ ] 事务使用连接池中的专用连接

### 3.2 [M-02] 硬编码 Telegram DC IP

**文件**: `lib.rs:235`

**问题**: `"149.154.167.50:443".parse().unwrap()` — IP 变动会导致 panic。

**解决方案**: 通过 `server_config.rs` 可配置，从环境变量或 `telegram_config` 端点获取。

**验收标准**:
- [ ] DC IP 可在环境变量中配置
- [ ] `.unwrap()` 替换为优雅错误处理
- [ ] 默认值仍然可用

### 3.3 [M-03] WebDAV 密码比较非恒定时间

**文件**: `webdav_routes.rs:26`

**问题**: Basic Auth 密码对比不是恒定时间。

**解决方案**: 复用 `http_middleware::constant_time_eq`。

### 3.4 [M-04] X-Forwarded-For 信任策略

**文件**: `access_lockout.rs:64-76`

**问题**: 无条件信任 `X-Forwarded-For` 头，攻击者可伪造 IP 绕过锁。

**解决方案**: 添加 `TRUSTED_PROXIES` 配置，仅信任已知代理 IP 的转发头。

### 3.5 [M-05] Share Cookie 使用 HMAC

**文件**: `share_routes.rs:36-41`

**问题**: Cookie 值使用裸 SHA-256(token || hash)，可能受长度扩展攻击。

**解决方案**: 使用 `hmac::Hmac<Sha256>`。

### 3.6 [M-06] 速率限制器内存泄漏

**文件**: `http_middleware.rs`

**问题**: 前缀树修剪仅在访问时惰性执行，长时间运行有内存增长风险。

**解决方案**: 添加后台清理任务，定期清理过期条目。

```
.map_err(|e| AppError::Database(e.into()))?
```

## 7. DevOps & 部署升级

### 7.1 Docker 镜像瘦身

**当前**: 运行时镜像约 800MB（含 GTK/WebKit 依赖）。

**优化方案**:
1. 为 `headless-server` 构建创建无 GTK 的运行时镜像（可缩减至 <200MB）
2. 使用 `distroless` 或 `alpine` 基础镜像
3. 多阶段构建已经实现，进一步优化层缓存

### 7.2 CI/CD 增强

| `trivy` 容器扫描 | Docker 镜像安全扫描 |

| Pre-commit hooks | 格式化/lint/类型检查 |
| 自动版本生成 | 基于 git tag 的版本号同步 |
