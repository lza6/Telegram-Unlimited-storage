## 5. 根本原因分析

### [P0-01] 上传中断不可恢复

**表面现象**：大文件上传到 80% 网络断开，刷新后必须从 0% 重新开始。

**直接原因**：`transfers.py` 的 `ProgressState` 仅存内存（`session_id → ProgressState`），无分片级 manifest 落盘；upload_chunks 表只有 `status: pending/complete`，无 `sha256` 校验后幂等重传语义。

**系统性原因**：
1. v5.0 聚焦于"能上传"，未考虑"断了能续"
2. Telegram 消息不可变，不能"追加分片"——必须客户端持有 manifest，服务端只做幂等接收
3. Bot API 单文件 20MB 限制（`bot_transport.py:21`）迫使大文件分片，但分片元数据未持久化

**影响半径**：
- `/api/v1/files` POST 上传
- `/upload`, `/merge_chunks` legacy 路由
- 所有 >50MB 文件的用户体验

**最小验证**：在上传 50% 时 `kill -9` 客户端，重启后检查是否可从 50% 续传。

---

### [P0-02] 版本号 3 处不一致

**表面现象**：`/api/v1/health` 返回 `"version": "2.0.0-python"`，但 CHANGELOG 已到 4.0.0，CLAUDE.md 声明 5.0.0。

**直接原因**：
```python
# state.py:36
return "2.0.0-python"
# main.py:338
version="2.0.0-python",
```

**系统性原因**：硬编码字符串，无单一来源（Single Source of Truth）。v3→v4→v5 升级时改了 CHANGELOG 但忘了代码。

**影响半径**：监控告警、调试日志、API 契约、用户困惑。

**最小验证**：`curl http://127.0.0.1:1334/api/v1/health | jq .version` 应与 `pyproject.toml`/`__init__.py` 一致。

---

### [P1-04] SQLite 同步访问瓶颈

**表面现象**：`storage.py` 使用 `sqlite3` 同步驱动 + `threading.Lock`，FastAPI `async def` 路由中通过 `asyncio.to_thread` 包装。

**直接原因**：sqlite3 是 C 扩展，调用时持有 GIL；模块级锁意味着所有表共享一把锁。

**系统性原因**：v5.0 优先保证 schema 与 Rust 版兼容，性能优化推迟。

**量化推断**（无基准测试，标注为推断）：
- 单连接 WAL 模式读并发 OK
- 写并发 = 1（SQLite 本质限制）
- `asyncio.to_thread` 线程池默认 40 线程，但锁使实际并发 = 1

**解决方向**：
1. 短期：表级锁拆分 + 读连接池（WAL 下多读单写）
2. 中期：`aiosqlite` 替换（API 兼容 sqlite3）
3. 长期：可选 PostgreSQL 控制面（roadmap.md P0 已列）

---

### [P1-05] 9 页面 sidebar 重复

**表面现象**：`dashboard.html:40-72`、`files.html`、`shares.html` 等 9 处复制粘贴相同 `<aside class="sidebar">` 结构。

**直接证据**：
```html
<!-- dashboard.html:40-72 -->
<aside class="sidebar">
  <strong class="brand-lockup">Telegram Drive</strong>
  <nav class="sidebar-nav">...
```
相同结构在 files.html / shares.html / settings.html / upload.html / docs.html / telegram.html / login.html / index.html 重复。

**系统性原因**：静态 HTML 无模板引擎，无构建步骤。

**解决方案对比**：
| 方案 | 优点 | 缺点 | 推荐 |
|------|------|------|------|
| A. 原生 Web Components (`<td-shell>`) | 无构建，浏览器原生 | 学习成本 | ✅ **推荐** |
| B. 构建时 SSI/模板（Jinja2 预渲染） | 输出仍是静态 | 加构建步骤 | 备选 |
| C. 客户端 JS include | 简单 | SEO/首屏差 | 不推荐 |

### [TASK-P0-03] 传输 Saga（崩溃恢复 + 孤儿消息清理）

| 属性 | 值 |
|------|-----|
| **优先级** | P0（架构）/ P2（实施可分阶段） |
| **风险等级** | L3 |
| **类型** | 架构 |
| **预估工时** | 3 天 |

**问题**：上传流程 = ① 发 Telegram 消息 → ② 写 file_assets 表。若 ① 成功 ② 失败（崩溃/DB 错误），Telegram 侧出现孤儿消息，DB 无记录，浪费存储且无法下载。

**方案**（Saga 模式 + 补偿事务）：

1. **新增 `saga_uploads` 表**：
```sql
CREATE TABLE saga_uploads (
    saga_id TEXT PRIMARY KEY,
    state TEXT NOT NULL,  -- started|tg_sent|db_written|completed|compensating|compensated
    message_id INTEGER,
    peer_id INTEGER,
    file_name TEXT,
    file_size INTEGER,
    owner_id TEXT,
    idempotency_key TEXT UNIQUE,  -- 客户端生成，防重
    created_at INTEGER,
    updated_at INTEGER
);
```

2. **状态机**（`backend/app/saga.py`）：
```
STARTED → TG_SENT (发 Telegram 成功，记 message_id)
TG_SENT → DB_WRITTEN (写 file_assets 成功)
DB_WRITTEN → COMPLETED (清理 saga 行)
TG_SENT (崩溃恢复) → COMPENSATING (删除 Telegram 消息) → COMPENSATED
```

3. **恢复 worker**（lifespan 启动）：
   - 每 60s 扫描 `state=TG_SENT AND updated_at < now-300` 的 saga
   - 尝试补偿（删 Telegram 消息）或完成（补写 DB）
   - 幂等键保证同一上传不会被重复执行

4. **集成点**：`routers/files.py` 上传端点改为 saga 编排。

**验收标准**：
- [ ] 模拟 ① 成功后 kill -9，重启后 60s 内孤儿消息被清理
- [ ] 同 idempotency_key 重试返回相同结果
- [ ] saga 表定期清理（保留 7 天审计）

# backend/app/rbac.py
SCOPES = {"read", "write", "delete", "share", "admin"}

def require_scope(scope: str):
    async def dependency(request: Request):
        identity: CallerIdentity = await get_identity(request)
        if identity.kind == "tenant":
            tenant = storage.get_tenant(identity.tenant_id)
            if scope not in tenant.scopes:
                raise HTTPException(403, f"missing scope: {scope}")
        return identity
    return dependency

# 路由使用

## 14. Red Team 事前反证

### 假设 1：断点续传"实现后"用户体验完美

**被当成事实的假设**：分片幂等 + manifest 落盘后，续传无缝。

**可能被遗漏的失败场景**：
- 客户端 localStorage 被清，manifest 丢失 → 仍从头传（降级而非失败）
- 服务端 `upload_sessions` 过期清理任务误删活跃 session
- SHA-256 计算大文件阻塞主线程（Web Worker 未用）
- 同一文件两个浏览器标签同时传 → manifest 冲突

**最小证伪实验**：
```bash
# 1. 上传 50% 清 localStorage → 验证降级为全量重传而非报错
# 2. 上传 50% 等服务端 session 过期 → 验证重新 init 不冲突
# 3. 两个标签同时传同一文件 → 验证后写者拒绝或合并
```

---

### 假设 2：SQLite 异步化"完成后"性能飙升

**被当成事实的假设**：aiosqlite 替换后并发大幅提升。

**可能被遗漏的失败场景**：
- SQLite 本质单写，异步化只提升读并发
- WAL 模式下写锁升级死锁
- `asyncio.to_thread` 线程池耗尽（默认 40）
- 连接池连接泄漏（异常路径未 close）

**最小证伪实验**：
```bash
# wrk 压测对比
wrk -t8 -c100 -d30s http://127.0.0.1:1334/api/v1/files
# 同步 vs 异步 p95 对比；若提升 <20% 则不值得
```

---

### 假设 3：RBAC"上线后"多租户安全

**被当成事实的假设**：scope 中间件加上后，租户隔离完美。

**可能被遗漏的失败场景**：
- 某路由忘记加 `Depends(require_scope(...))` → 默认放行
- `owner_id` 过滤漏加 → tenant A 看到 tenant B 文件
- WebDAV 路由绕过 RBAC（独立认证逻辑）
- legacy 路由未接入 RBAC

**最小证伪实验**：
```python
# 自动化：遍历所有路由，断言都有 scope 依赖
for route in app.routes:
    if route.path.startswith("/api/v1/") and route.methods != {"GET", "HEAD"}:
        assert any(isinstance(d, Depends) and "require_scope" in str(d) for d in route.dependencies)
```

---

### 假设 4：组件化"重构后"前端零回归

**被当成事实的假设**：`<td-shell>` 替换后 9 页面行为一致。

**可能被遗漏的失败场景**：
- 组件内事件监听与页面脚本冲突（事件委托层级变化）
- CSP nonce 注入不覆盖 Shadow DOM
- 组件未注册时 FOUC（需 `:not(:defined) { display: none }`）
- 某页面 sidebar 有定制项被一刀切

**最小证伪实验**：
- Playwright 截图对比 9 页面前后（像素级 diff）
- 每页面 axe-core + 键盘导航回归
