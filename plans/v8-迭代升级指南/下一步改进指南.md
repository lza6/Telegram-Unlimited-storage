### 1.3 已知遗留问题（v7.0 → v8.0 必须解决，**全部基于真实代码证据**）

| ID | 问题 | 证据 | 影响 |
|----|------|------|------|
| **W-01** | `storage.py` 仍是**全同步 sqlite3 + 模块级 `threading.Lock`** | `storage.py:1-10` 文档自述同步；`:192 _read_conn`、`_write` 用 sqlite3.Connection | 高并发写 = 1，GIL + 锁竞争，v7 虽加了 PG 但默认仍走 SQLite |
| **W-02** | `storage_pg.py` 与 `storage.py` **双存储并存无统一抽象层** | `storage.py`（同步）与 `storage_pg.py:104`（异步 `asyncpg`）API 不一致，路由层需 if/else | 维护成本高，切换风险大 |
| **W-03** | FTS5 无**自动同步触发器**，依赖 `fts_insert` 手动调用 | `storage.py:675-703` 仅有 `fts_insert/fts_delete/fts_search` 方法，无 `CREATE TRIGGER` | 删除/重命名文件后 FTS 索引漂移，搜索结果过期 |
| **W-04** | `legacy.py` 653 行，**向后兼容包袱重** | `routers/legacy.py`（653 行）维护 `/upload`、`/merge_chunks` 等旧接口 | 测试覆盖 22%，重构/迁移风险源 |
| **W-05** | 测试**无覆盖率门槛强制** | `pytest.ini` 仅 `addopts = -q`，无 `--cov-fail-under` | 覆盖率可无声回退，270 用例但无量化基线 |
| **W-06** | **无 mypy / ruff 配置文件** | `backend/` 下无 `pyproject.toml`/`mypy.ini`/`ruff.toml` | 类型安全无保障，lint 无统一标准 |
| **W-07** | **无 CI/CD 工作流** | `.github/workflows/` 目录不存在或为空 | 推送即可能破坏主干，无自动化质量门 |
| **W-08** | 前端**仅 1 个 Web Component**，组件化未完成 | `deploy/web/components/` 仅 `td-shell.js` | 文件卡、分享卡、上传卡仍重复 DOM |
| **W-09** | **无文件预览**（缩略图/视频海报/PDF.js） | `files-core.js` 无 `<img>` 缩略图逻辑、无 `<video poster>`、无 PDF 渲染 | 用户体验落后于竞品 |
| **W-10** | Service Worker **无后台同步 / 离线队列** | `service-worker.js` 142 行仅缓存策略 | 断网时上传无队列暂存 |
| **W-11** | **无结构化日志**（仍是 `logging.getLogger`） | `transfers.py:logger = logging.getLogger(...)` | 无 trace_id 关联，排障困难 |
| **W-12** | **无 OpenTelemetry 链路追踪** | 全局无 `opentelemetry` import | 跨模块/跨 Telegram 调用链不可观测 |
| **W-13** | 下载**无 ETag / 条件请求**（If-None-Match/If-Modified-Since） | `routers/files.py:297 download` + `shares.py:350 /d/signed` 无 ETag 头 | 重复下载浪费带宽，CDN 友好度差 |
| **W-14** | **无幂等键持久化**（`TransferManager._idempotency_locks` 仅内存） | `transfers.py:93` `_idempotency_locks: dict[str, asyncio.Lock]` | 重启后重放窗口丢失，重复上传风险 |
| **W-15** | **无配额告警 / 预测** | `quota.py` 仅预校验拒绝，无阈值告警 | 用户撞墙才知道超额 |
| **W-16** | **无备份恢复演练**（DB 备份存在但无恢复测试） | `routers/health.py` 备份逻辑存在，无 restore 路径 | 灾备"备份了没恢复过"的经典坑 |
| **W-17** | **无 secret 扫描 / SAST 集成** | 项目根无 `.github/workflows`、无 `gitleaks`/`semgrep` 配置 | 密钥泄漏无自动拦截 |

## 2. 执行摘要

### 2.1 当前阶段定位

Telegram Drive v7.0 已完成 **7 大主线**（传输可靠性 / 版本统一 / 密钥轮换 / 多租户 RBAC / PG 控制面 / 前端组件化 / 传输中心 UI），功能层面已达"完备"。但距离"**生产级 SaaS 顶尖水准**"仍有 **17 项明确差距**（W-01 ~ W-17），集中在：

- **存储层未异步化**（W-01/W-02）：SQLite 同步锁仍是高并发硬瓶颈
- **可观测性缺链路**（W-11/W-12）：无结构化日志、无分布式追踪
- **工程化基础设施缺失**（W-05/W-06/W-07/W-17）：无覆盖率门槛、无 mypy/ruff、无 CI、无 SAST
- **前端体验未达顶尖**（W-08/W-09/W-10）：组件化未完成、无预览、无离线队列
- **可靠性细节欠打磨**（W-03/W-13/W-14/W-16）：FTS 漂移、无 ETag、幂等不持久、灾备未演练

### 2.2 v8.0 八大升级主线

| # | 主线 | 类别 | 优先级 | 预估工作量 | 对应问题 |
|---|------|------|--------|-----------|----------|
| 1 | **存储层统一异步抽象 + SQLite → aiosqlite 迁移** | 性能/架构 | **P0** | 4 天 | W-01/W-02 |
| 2 | **工程化基础设施（CI + mypy/ruff + 覆盖率门槛 + SAST）** | 工程质量 | **P0** | 3 天 | W-05/W-06/W-07/W-17 |
| 3 | **结构化日志 + OpenTelemetry 分布式追踪** | 可观测性 | **P1** | 4 天 | W-11/W-12 |
| 4 | **前端组件体系 + 文件预览 + 离线后台同步** | UI/UX | **P1** | 5 天 | W-08/W-09/W-10 |
| 5 | **HTTP 缓存层（ETag / 条件请求 / CDN 友好）** | 性能 | **P1** | 2 天 | W-13 |
| 6 | **幂等键持久化 + 传输持久化队列** | 可靠性 | **P1** | 3 天 | W-14 |
| 7 | **配额告警 + 灾备演练 + FTS 自动同步** | 运维/可靠性 | **P2** | 3 天 | W-03/W-15/W-16 |
| 8 | **legacy 路由迁移 + 向后兼容收口** | 工程质量 | **P2** | 2 天 | W-04 |

### 2.3 推荐总体实施顺序

```
Phase 0 (1天):   P0 工程化基线（mypy/ruff + 覆盖率门槛）→ 立刻拦截回归
Phase 1 (4天):   P0 存储层异步抽象层（不破坏 SQLite 现有语义）
Phase 2 (2天):   P0 CI/CD + SAST 流水线
Phase 3 (4天):   P1 结构化日志 + OpenTelemetry
Phase 4 (2天):   P1 HTTP 缓存层（ETag/条件请求）
Phase 5 (5天):   P1 前端组件体系 + 文件预览 + 离线队列
Phase 6 (3天):   P1 幂等持久化 + 传输持久化队列
Phase 7 (3天):   P2 配额告警 + 灾备演练 + FTS 触发器
Phase 8 (2天):   P2 legacy 收口 + 向后兼容清理
Phase 9 (持续):  P3 性能调优 / 智能能力扩展（语义搜索 / ML 分类）
```

### 2.4 最大交付风险

| 风险 | 缓解措施 |
|------|---------|
| **SQLite → aiosqlite 破坏事务语义** | 先建 `StorageBackend` 抽象层，SQLite/PG 双实现，灰度切换，保留同步实现作回退 |
| **legacy 路由迁移破坏存量用户** | 保留路由但内部转发新 API，加 deprecation 头，不删端点 |
| **OpenTelemetry 性能开销** | 采样率默认 10%，保留开关 `OTEL_ENABLED=false` |
| **ETag 计算成本** | 用文件 sha256 + mtime 弱校验，避免每次全量哈希 |
| **前端组件化回归** | `<td-shell>` 已验证，逐个组件迁移，每步可视化对比 |

## 5. 根本原因分析

### [P0-01] SQLite 同步锁瓶颈

**表面现象**：高并发上传/下载时 API 延迟飙升，CPU 在 GIL + 锁等待上空转。

**直接原因**（真实代码）：
```python
# storage.py:1-10 文档自述
"""The class is synchronous (sqlite3); FastAPI routes that touch it
should be plain ``def`` so they run in the threadpool, or call via
``asyncio.to_thread``."""

# storage.py:192 _read_conn / _write 用 sqlite3.Connection（同步 C 扩展，持 GIL）
# 模块级 threading.Lock 意味着所有表共享一把锁
```

**系统性原因**：
1. v5.0 优先保证与 Rust 版 schema 兼容，性能优化推迟
2. v7.0 加了 `storage_pg.py` 但**未建统一抽象层**，路由层仍默认走 SQLite
3. SQLite 本质：WAL 下读并发 OK，但**写并发 = 1**（写锁串行）

**量化推断**（无基准测试，标注为推断）：
- 单连接 WAL 读：并发无上限
- 写：严格串行（SQLite 限制）
- `asyncio.to_thread` 默认 40 线程，但锁使实际写并发 = 1

**影响半径**：所有触碰 `storage.py` 的路由（files/shares/transfers/quota/health）

**最小验证**：`locust` 或 `wrk` 压测 `/api/v1/files` POST 并发 10，观察 p95 延迟与写锁等待时间。

---

### [P0-02] 无工程化基线（mypy/ruff/覆盖率门槛）

**表面现象**：270 个测试无量化覆盖率，无类型检查，无 lint 统一。

**直接原因**：

`backend/` 下无 `pyproject.toml`、无 `mypy.ini`、无 `ruff.toml`。

**系统性原因**：v5→v7 聚焦功能交付，工程化基础设施作为"以后再做"持续推迟。

**影响半径**：每一次 PR 都可能无声回退覆盖率、引入类型错误。

### [P0-03] 无 CI/CD + 无 SAST

**表面现象**：`.github/workflows/` 不存在或为空，推送 `main` 无自动校验。

**直接原因**：项目根 `.github/` 目录虽有，但无 workflow 文件。

**系统性原因**：自托管项目未接入 GitHub Actions。

**影响半径**：主干可能被破坏性提交污染，密钥泄漏无自动拦截（W-17）。

**表面现象**：排障靠 `grep` 日志文本，无 trace_id 串联跨模块调用。

### [P1-03] 无 ETag / 条件请求

**表面现象**：重复下载同一文件每次全量传输，无 304 Not Modified。

**直接原因**：

**影响半径**：所有下载流量，CDN 缓存命中率为 0。

**系统性原因**：幂等设计为单进程内存锁，未考虑多 worker / 重启场景。

**影响半径**：重启窗口内的重复上传、重复 Saga。

```sql
END;
```

## 16. Red Team 事前反证

### 假设 1：aiosqlite 迁移"无损"

**被当成事实的假设**：换 aiosqlite 后行为完全等价。

**可能被遗漏的失败场景**：
- aiosqlite 的事务隔离级别与 sqlite3 不同
- 连接池下 WAL 的写锁行为变化
- 某些 `PRAGMA` 在连接池中需每连接重设

**最小证伪实验**：参数化测试对比 `Storage`（同步）与 `SQLiteBackend`（异步）的 10 并发写，校验结果一致 + 无死锁。

---

### 假设 2：ETag 提升"一定省带宽"

**被当成事实的假设**：ETag 必然减少下载流量。

**可能被遗漏的失败场景**：
- 客户端不带 `If-None-Match`（如 curl 默认）
- ETag 计算成本 > 节省的带宽（小文件）
- CDN 不缓存签名 URL（路径含 token）

**最小证伪实验**：对比开关 ETag 前后的出口流量 + ETag 计算耗时。

---

### 假设 3：OTel "无性能开销"

**被当成事实的假设**：`OTEL_ENABLED=false` 时零开销。

**可能被遗漏的失败场景**：
- instrumentation 仍在创建 span（即便不导出）
- structlog JSON 序列化比文本日志慢

**最小证伪实验**：基准压测对比 `OTEL_ENABLED` true/false 的 p95。

---

### 假设 4：旧产物清理"无害"

**被当成事实的假设**：删 `server-e2e.log`/`x.tmp`/`.env.backup-*` 无影响。

**可能被遗漏的失败场景**：
- `.env.backup` 是某次配置丢失的唯一备份
- `server-e2e.log` 是正在排查的 bug 现场
- `backups/` 含未归档的历史

**最小证伪实验**：清理前 `git log --all --full-history -- <file>` 确认非唯一来源 + 用户确认。
