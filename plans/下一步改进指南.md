## 6. 根本原因分析

### [P1-01] httpx AsyncClient 无重试

**表面现象**：`bot_transport.py` 中 `httpx.AsyncClient` 初始化时未配置重试策略。

**直接原因**：
```python
# bot_transport.py:60-65 (当前代码)
self._client = httpx.AsyncClient(
    timeout=httpx.Timeout(300.0, connect=15.0),
)
```

**系统性原因**：Bot 传输模式是后加的功能，初期实现时关注点集中在 API 调用正确性，未考虑网络抖动的容错。

**影响半径**：
- `/api/v1/files` POST 上传（bot 模式）
- `/api/v1/files/bulk` 删除（bot 模式）

**最小验证方法**：检查 `bot_transport.py` 中 `AsyncClient` 是否配置了 `retries` 参数。

---

### [P1-02] 审计日志未集成

**表面现象**：`audit.py` 定义了完整的 `AuditLogger` 类和事件枚举，但所有路由文件（`shares.py`、`files.py` 等）均未调用。

**直接原因**：审计模块是按计划先定义后集成的，定义完成后未完成集成步骤。

**系统性原因**：分阶段实现中，审计日志作为"未来增强"功能，优先级低于核心上传下载。

**影响半径**：
- 无法追踪敏感操作（认证成功/失败、文件删除、分享访问）
- 合规审计缺失

**证据**：
```python
# audit.py:20-50 定义完整
class AuditEvent(str, Enum):
    AUTH_SUCCESS = "auth.success"
    FILE_DELETE = "file.delete"
    ...

# 但 shares.py, files.py 等路由中无任何 audit.log 调用
```

### [TASK-P1-01] httpx AsyncClient 重试配置

| 属性 | 值 |
|------|-----|
| **优先级** | P1 |
| **风险等级** | L1 |
| **类型** | 缺陷修复 |

| **证据** | `bot_transport.py` |

**推荐方案**：
```python
# bot_transport.py 修改
from httpx import AsyncHTTPTransport

transport = AsyncHTTPTransport(retries=3)
self._client = httpx.AsyncClient(
    transport=transport,
    timeout=httpx.Timeout(300.0, connect=15.0),
)
```

**下游影响**：Bot 模式上传稳定性提升

## 13. Red Team 事前反证

### 假设 1：httpx 重试"修复后"问题消失

**被当成事实的假设**：添加重试后，上传失败问题解决。

**可能被遗漏的失败场景**：
- Telegram Bot API 本身速率限制
- 频道满/不存在等业务错误（非网络错误）
- Bot Token 失效

**触发条件**：连续重试 3 次后仍然失败

**失败成本**：日志可能淹没、用户体验更差

**最小证伪实验**：
```bash
# 模拟 502，验证重试行为
curl -X POST /api/v1/files -d "test" --local-fault-injection
```
